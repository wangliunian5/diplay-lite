## 无线连接提速定案（20261012 晚，TS7 实测，versionCode 65/66）

背景：10-12 TS7 三份日志（204308 vc65 / 205800 vc66）+ 0.2.6-ch 四样本对比。vc64 基线 104~107s（首轮必失败 2 轮）；根因链 = BT profile proxy 查询 8s + First TCP 看门狗 30s 恰好杀在 iPhone 入网途中（实测入网 25~35s）+ 每轮失败 teardown 拆热点把 iPhone 踢下网 + Bonjour start/close 各阻塞 7~8s。

- vc65（1.1.4）：①BT 单台直选（唯一 bonded iPhone 跳过 HFP/A2DP profile proxy，省 ~8s）；②First TCP 看门狗 30s 后加 35s 宽限复查，窗口内 TCP 进入即放行；③重试/看门狗失败路径 `closeWirelessStack(keepHotspotForReuse=true)`，热点常开 iPhone 不掉网（对齐 0.2.6 模式）；④Bonjour close 异步化（goodbye 限时 300ms）。实测 Manual 15.4s / Relay 17.3s，失败循环消失
- vc66（1.1.4）：Bonjour start() 整体后台化（204308 日志坐实 JmDNS create+register 同步 7.5s 才是关键路径真凶；BT 快路径已生效后空隙仍在）。竞态护栏：代次过期自查 close / lifecycleLock 兜底 / bonjour 字段引用比较。实测 Manual **11.5s** / Relay **13.3s**，已贴 0.2.6 水平（4.6~12.1s）
- 遗留：`bt socket closed, read return: -1`（iPhone 收流后关引导链）仍会偶发掉线，靠手点重连恢复——归入隧道提级专项

## TS7 有线 CarPlay 突破（20261013 晚，vc68→vc75，✅ 已全线打通）

### 根因链（四层，全部实测实锤）
1. **iOS16.x 在 NCM 链路上必须 mDNS 发现 `_airplay._tcp`/`_raop._tcp` 才起数据面**——0x4301 直给的 fe80::2:7100 不被采用（包级实锤：iPhone 在 NCM 上发 mDNS 查询 4 次，t=43.6s 起）
2. **MUSB EP 0x07 TX 静默丢弃**：配置 6 有两对 NCM 接口组（3/4 组 OUT=0x06 带 interrupt EP 0x87；5/6 组 OUT=0x07 无 interrupt EP）。Lite 原选 5/6 组，iPhone 永远收不到帧；0.2.6-ch 在 TS7 死于自己的 UsbRequest.queue 16KB 上限崩溃（MUSB 特有约束，K60 无此约束、ch 在 K60 正常）未构成对照。vc70 反转选组后 iPhone 首次真实连入（tcp→7100 + 1500B 视频帧）
3. **MUSB RX 高流量/静态期丢包致 NTB16 字节流错位**（每次丢 3 字节，头部多为 000000）：一次签名校验失败即 failSession 拆桥（vc71 实测：画面已出、activeStreams=[110]，满流时一包毁全会话）
4. **内核 cdc_ncm 每 2-4s 重绑 6.3**：与 App usbfs claim 打架（内核侧额外控制传输），PC 外置解绑循环（2s 巡检）期间会话稳定

### 各版本修复
- **vc68**：新增 WiredBonjourAdvertiser——有线模式在 tun 地址（fe80::2）上 JmDNS 注册 `_airplay._tcp`+`_raop._tcp`（TXT 与无线一致），后台线程启动非致命降级
- **vc69**：建立看门狗 15s→30s（JmDNS 注册实测 ~10s，15s 只剩 5s 应答窗口）
- **vc70**：NcmUsbBridge 选组反转为优先 3/4（OUT=0x06 + interrupt EP 0x87）+ 内核 cdc_ncm 解绑外置循环 → **iPhone 首次连入，画面首现**
- **vc71**：看门狗 30s→60s——iPhone 在 TS7 的 mDNS 问答收敛要 ~30s，30s 上限在数据到达前 57ms 误杀（19:51:20 实测）
- **vc72**：NTB16 失步重同步——签名校验失败不再 failSession，向前扫描丢错位前缀对齐下一签名（保留尾 3 字节拼接），丢帧花屏由 keyframe recovery 兜底
- **vc73**：风暴计数窗口化——累计 64 上限在静态画面期（错位 ~1-2 次/秒）2.5 分钟自拆（20:26:18 实测），改为 30s 无错位重置 + 窗口 256
- **vc74/75**：WiredNcmGuard 内置守护（2s 扫 /sys/bus/usb/devices，su 写 driver/unbind，无 root 静默降级）——vc74 曾解绑全部 6.x 导致已 claim 的 6.4 被解绑、alt 复位打死 bulk-out（"bulk-out not ready" 两窗口全超时），vc75 收窄为只解绑 6.3（外置守护的成功行为）

- **Carlinkit 硬件逆向（ludwig-v/wireless-carplay-dongle-reverse-engineering）**：盒子 SoC 为 i.MX6ULL（与 EU5 同族），蓝牙/WiFi 为 Realtek RTL8822BS/CS、Marvell、Broadcom、NXP IW416 组合芯片走 SDIO——**官方盒子不用 CSR8510**。即 H52 外挂 CSR8510 是其自有选择，动机大概率是绕开车机内置蓝牙栈的烂质量（与我们 8815 可见性/RFCOMM 带宽痛点同源）
- **CSR8510 外置路线的开源参照**：45clouds/WirelessCarPlay（RPi+bluez，BLE 握手+WiFi 建链，USB 转发车机）、dirkx/osx-hid2hci-for-bluetooth-csr8510-A10 与 hhsnake/csr8510-fix（CSR8510 HID→HCI 模式切换与山寨芯片 Linux btusb 修复）
- **对 DiPlay 的启发与取舍**：外挂 USB BT 路线在 Android 上成本高（需自碰 HCI 层，bluez 不适用，且要处理 btusb/HID 代理模式），**优先级低**；当前收益最大的是 catplay 源码挖掘（MFi 身份假设对照 + iAP2 隧道参照）。8815 蓝牙可见性问题继续走软件自动拉起可见性路线（见上方待分析项）

## CSR8510 dongle 方案（20261017 深夜调研，归档为补充知识——非当前主攻）

> **定位（20261018 定案）**：dongle 条目降级为**补充知识/技术储备**。FE-6 无线主攻改为 **USB bootstrap 无线升级路径**（见下一节）；dongle 保留给「无可用有线 iAP2 通道」的机型（如 8815 老插口无法有线），将来需要时按此蓝图启动。

**触发（调研缘由）**：FE-6 蓝牙四层全死定案（REPORT.md：GOC 私有后端 + SPP 空壳 + native 门控编译期阉割 + libbt-vendor.so 缺失）→ 内置栈无出路，外挂 dongle 是绕开内置栈的兜底路线。vc101 的 USBDEVFS_DISCONNECT_CLAIM 可直接复用（踢 btusb/usbhid 抢绑）。

**架构**：CSR8510 USB dongle（H4 HCI）→ usbfs control+bulk 直发 HCI → 自实现协议栈（HCI→L2CAP→RFCOMM→iAP2）→ BtBootstrap 接口无缝替换（上层 iAP2/0x5703/0x4301/WiFi 全复用，BT 只做 bootstrap）。

**参照系**：45clouds/WirelessCarPlay（握手序列）、hhsnake/csr8510-fix + dirkx/osx-hid2hci-for-bluetooth-csr8510-A10（HID→HCI 模式切换/山寨芯片）、catplay（iAP2）、FreeAuto usbbt 包（纯软件 HCI 栈移植源，用户指认）。

**里程碑（启动时按此执行）**：
- M1 通路验证：DongleIdentity（运行时读 VID/PID 非白名单）+ usbfs 打开 + HCI Reset/Read BD_ADDR → adb 日志实锤。**风险前置**：CSR8510 出厂 HID 代理模式需 vendor 命令切 HCI（参照 osx-hid2hci）
- M2 链路建立：HCI 引擎（命令/事件/ACL）+ page scan/accept + L2CAP PSM RFCOMM + RFCOMM 会话 → iPhone 端发起 iAP2 建链全通（识别/MFi/0x5702/0x4e0d/0x4e0e/0x4300）
- M3 会话闭环：iAP2 隧道接回现有 Csm/0x5703/0x4301 + WiFi 建链（原栈零改动）→ 无线 CarPlay 画面出
- M4 实装：8815（需 iPhone 忘掉内置配对避免双 BT 干扰）→ C8815

**风险清单**：山寨 CSR8510 兼容（hhsnake 修复参照）；HCI ACL 缓冲吞吐是否撑得住 iAP2 隧道（对照 8815 内置栈带宽痛点，M2 实测）；iPhone 端双 BT 目标混淆（M4 处理）；蓝牙地址/MFi 身份与 dongle 绑定（_identity 持久化沿用）。

## FE-6 无线主攻：USB bootstrap 无线升级路径（20261018 立项，当前最高优先级）

**官方背书**：Apple 官方 iPhone 手册（iph6860e6b53）第②条连接路径原文——「如果你的车支持通过无线方式和 USB 连接线使用 CarPlay 车载：将 iPhone 接入 USB 端口。**下次尝试连接时，iPhone 上的提醒可让你无线连接**」。即「首次有线 → iPhone 弹提醒 → 升级无线」是 Apple 标准流程，Carlinkit U2W 只是复刻（其盒子无蓝牙，纯 USB 设备照样做无线 CarPlay）。

**FE-6 现成条件**：有线已通（wedge→auto-retry 回归通过）= iAP2 over USB 隧道现成；0x5703/0x4301 消息构造已有（中继模式在用）；AP 开启代码已有；FE-6 有线会话已在 iPhone CarPlay 列表留有配对记录（第③条流程的现成资产）。

**缺口清单（即工作量）**：
1. 0x4e0e capabilities 补 wireless 能力位（有线模式现在只报 wired）——iPhone 能弹「无线连接」提醒的前提
2. 0x5703 WiFi 凭据改经 USB 隧道发出（承载从 BT RFCOMM 换 USB，协议零改动）
3. iPhone-initiated mDNS 直连的接受侧（type-130，iOS16 mDNS 依赖既有记录）

**与 dongle 的关系**：本路径通则 FE-6 无需 dongle；dongle 的 M3 与本路径技术重叠，做完本路径 dongle 即使要上也只剩 M1/M2。

**行动**：FE-6 实测第一步——有线会话日志查 0x4e0e 能力位现状 → 落码补位。前置：无（与 T3 有线并行）。

### USB bootstrap 实施方案定案（20261018 深夜，vc102 = 首个测试包）

**架构关键发现**：无线 CarPlay 的蓝牙 RFCOMM 只承载 iAP2 控制面，音视频走 AirPlay TCP。把承载从 RFCOMM 换成 USB 隧道后，**线只跑 iAP2 控制面、媒体全走 WiFi——NCM 数据面整体不需要**。有线栈的 NCM 桥/claim 数据接口/cdc_ncm 抢绑/alt=0/T3 四坎全部绕开；唯一保留 usbmux→carkit→CSM 控制隧道（FE-6 已验证稳定）。

**流程（对照现有代码）**：
- 阶段A（复用 runWiredStack 前半程 L2664-2702 原样）：发现→权限→usbmux→Lockdown 配对→carkit→CSM
- 阶段B（新分叉）：B1 开 AP（复用 WirelessHotspotManager）；B2 mDNS 广播（复用 bonjourClient，4.1 失败非致命）；B3 识别帧第三形态；B4 控制环直接用 Iap2WirelessControlClient.run()（只吃 Iap2Session，传输无关；订阅前补发 0xae03 电源通告）
- 阶段C（拔线）：USB CSM 死→CHANNEL_CLOSED→wirelessActiveReported=true→抑制拆除（镜像无线 handoff 保留逻辑 L1074-1089）

**三处改动**：
1. Iap2IdentificationClient：识别帧第三形态 group16(USBHostTransport)+group24(SSID)，无线消息列表（0x5703 发/0x4e0d+0x4e0e+0x5702 收）。现状 wired/wireless 二选一（L204-229）；FE-6 无蓝牙 MAC 正好只发 16+24——是否符合 Apple 预期是首个实测点
2. CarPlayController：有线分叉——CSM 开好后不进 NCM 段，改走 B1-B4（配置开关门控）
3. 关闭路径：CHANNEL_CLOSED 后按 wirelessActiveReported 决定保留；teardown 复用 closeWirelessStack

**不动**：MFi、AirPlay、pair-verify、触摸/音频/视频全链、AirPlay stall 看门狗（无线客户端自带）。

**实测四步判据（FE-6 首战）**：
1. 1D01 接受性：iPhone 回 1D02=组合可行；回 1D03 列被拒参数
2. 0x5702 到来 = 无线能力宣告生效；AP 侧见 iPhone 关联
3. 0x4301 无线版：iPhone 向 host IP 发 RTSP→AirPlay TCP→画面出
4. 拔线存活：线拔会话不塌（阶段C 生效）

**兜底**：1D03 拒收 group16+24 → 退一档试「只发 group24」或「group16+17+24（补假 BT MAC）」。Carlinkit 盒子带蓝牙，纯 USB 形态 Apple 侧接受度无公开先例，实测定生死。四步全过=FE-6 无线打通（无蓝牙无 NCM），T3 同样适用。
